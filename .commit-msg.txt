Fix HITL response corrupted to 'NOT SOURCED YET' on later reload

Root cause (save-time bug): the HITL message types — clarifying question
(needsInput), safety acknowledgment (safetyAck), and provider-busy fallback
— were rendered live but their msg.status was never set to a terminal value
(it stayed 'thinking') and their card data was never persisted. On a LATER,
unrelated reload, the static renderer saw 'thinking' and misread a completed
exchange as incomplete, showing 'NOT SOURCED YET — didn't finish processing'.

Fixes:
- Save-time: runPipeline now persists a terminal status + the card data for
  needsInput (question, field), safetyAck (question, context, token), and
  providersBusy (message, retryAfter) before rendering.
- Read-time: renderAgentMessageStatic recognizes these terminal statuses and
  re-renders the matching card — the clarifying question is still answerable
  after reload; safety approval re-renders with a working confirm (honest
  'Expired — ask again' if the ack token lapsed); provider-busy re-renders
  its message. The step trace is no longer invented for these states (they
  never had one live).
- finalizeStaleMessage is now a non-destructive safety net: it no longer
  nulls msg.result before checking it; a message with a stored result is
  marked 'done' and rendered, never clobbered.
- The answer result is persisted immediately (before streaming), so even a
  genuine mid-stream reload can recover the completed answer.
- The misleading error text is gone: interrupted messages now show an honest
  'Response incomplete' state that does not blame a reload that never
  happened, and 'Not sourced yet' is reserved for its real meaning (no
  ingested sources).

Added test-chat-hitl-reload.js covering the full repro: clarifying question
-> answer -> completed -> later reload -> card + answer preserved, and the
honest incomplete state for genuinely interrupted messages.
